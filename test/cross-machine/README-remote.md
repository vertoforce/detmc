# The remote half of the detmc cross-machine determinism pair

This directory runs one half of a two-machine determinism pair. Copy it to the
second machine (called host B below); the first machine (host A) runs the other
half out of `test/cross-machine/` in the repo. The point is to show that two servers
with the same jar, image, seed and command script produce the same world on two
different CPUs, not just twice on one host.

Results live on host A in `test/cross-machine/RESULT.md`.

## What must be identical on both machines

| Thing | Value |
|---|---|
| image | `itzg/minecraft-server:latest@sha256:c1a267d9ed6de3d1157859753a002aa35f8366d8db00463df3d6b07e86d2bf1d` |
| mod jar | `mods/detmc-0.1.0.jar`, sha256 in `out-*/params.txt` |
| world seed | `SEED=12345` (compose-det.yml) |
| detmc seed | `-Ddetmc.seed=1` (compose-det.yml) |
| JVM opts | `-Ddetmc.freezeOnStart=true -Dmax.bg.threads=1` plus `DETMC_EXTRA_OPTS` |
| harness env | `TARGETS`, `SPRINT_MARGIN`, `DETMC_EXTRA_OPTS` |
| server.properties | generated by the image from the compose env, so equal by construction; `xm-run.sh` saves a copy minus the rcon password line |
| rcon script | `run-det-xm.sh`, a byte copy of `test/run-det.sh` except `ctr=${CTR:-mc-det-$label}` |

Anything else is allowed to differ. That is the experiment.

## Re-run

On host B:

```bash
cd ~/detmc-xm
export TARGETS=24000 SPRINT_MARGIN=100000
export DETMC_EXTRA_OPTS="-Ddetmc.traceIo=true -Ddetmc.traceEntityWindow=0:3,2190:2210"
./xm-run.sh B mcB mc-det-hostB hostB > xm-remote.log 2>&1
```

`SPRINT_MARGIN=100000` is larger than the tick target on purpose: it forces the harness
to use `tick step` only and never `tick sprint`, so no window of the run is free-running
at 20 tps against the wall clock.

On host A, same env, the A half:

```bash
cd test/cross-machine
./xm-run.sh A mcA mc-xm-A hostA > xm-local.log 2>&1
```

Then copy `~/detmc-xm/out-hostB/` back to host A next to `out-hostA/` and run
`./xm-compare.sh`.

A 24000-tick half takes roughly an hour of wall clock on an idle host B; `tick step`
runs at the server tick rate and detmc serialises chunk work.

## Files

| File | What it is |
|---|---|
| `compose-det.yml` | copy of `test/compose-det.yml` with the container names changed to `mc-xm-A` and `mc-det-hostB` |
| `.env` | `RCON_PASSWORD` only, copied from `.env.example`. The same value on both machines, so `server.properties` matches. Not in git |
| `run-det-xm.sh` | the harness, one line changed from `test/run-det.sh` |
| `xm-run.sh` | one run: fresh data dir, start, record machine facts, run the harness, copy artifacts to `out-<tag>/`, remove the container |
| `region-md5.py`, `nbt-canon.py`, `analyze-ew.py`, `diff-det.sh` | copies of the `test/` comparison tools |
| `out-hostB/` | the artifacts of a run |

## Gotchas

- `MAX_TICK_TIME=-1` in the compose file is required. The tick-end chunk drain collapses a
  whole forceload into one tick and the default 60 s watchdog kills the server mid-generation.
- Docker log rotation must stay at `max-size 2g, max-file 1`. With `-Ddetmc.traceIo=true`
  the log passes 30 MB and the default 10m x 3 rotates the startup traces away, which
  silently truncates `ec-*.txt` and `trace-*.txt`.
- `save-all flush` over rcon returns an i/o timeout. It still runs; the harness waits for
  the mod's `saveEverything done` log line instead of the rcon reply.
- Raw `md5sum` of a region file can never match across runs: bytes 4096..8191 are a
  per-chunk wall-clock timestamp. Use `region-md5.py`, which blanks that table.
- `data get entity @s id` returns nothing, so the result file's "all entities id" section
  is empty in every run. Entity ids are only checked through the `[detmc-ew]` rows.
